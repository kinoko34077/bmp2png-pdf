# BMP → PNG/PDF リファクタリング設計書

- 作成日: 2026-10-09
- 状態: 実装承認済み（上書き時の接尾辞欄制御・フォルダー型配布を追加）
- 対象リポジトリ: `kinoko34077/bmp2png-pdf`
- 関連: Issue #1、PR #2

## 目的

既存の BMP→PNG/PDF ツールを、保守しやすく、配布物が軽く、画像変換とPDF生成の無駄な処理が少ない構成にする。利用者側に Python やネット接続を要求しない Windows x64 向けデスクトップソフトという方針は維持する。

## 採用方針

Python/Tkinter/Pillow を維持し、C/C# への全面移植は行わない。現在の処理規模では、Pythonから呼び出すPillowのネイティブ画像処理が主な変換を担う。言語移植だけでは速度向上を見込みにくく、GUI・画像・PDFライブラリの再選定と再実装が増えるためである。

PDF生成は ReportLab+pypdf を維持する。`img2pdf` は速度・PDFサイズで優位だったが、配布依存が大きく増えるため初回採用しない。PDF上の画像画素、DPI、A4レイアウト、初期表示設定を維持しつつ、PDF全体を一度メモリへ読み込む中間処理をなくす。

リファクタリング時点では起動時の展開を避けるため PyInstaller one-folder を選んだ。その後、利用者PCに管理者権限がないことと、単体アプリを求める要望を受け、2026-10-10にNuitka one-fileへ変更した。展開先を版ごとのユーザーキャッシュに固定するが、Nuitkaの固定キャッシュモードが起動時間を短縮するとは限らない。起動時にはファイル展開・確認処理があり、初回・次回の起動時間は対象PCで測定して判断する。詳細は[Nuitka one-fileの説明](https://nuitka.net/user-documentation/use-cases.html)を参照。

PDF方式は固定画像セットで比較した。4ページのPDF作成はReportLab+pypdfが0.491秒・242,410バイト、img2pdf+pypdfが0.171秒・230,848バイトで、ピークメモリはそれぞれ60.4MiB、60.8MiBだった。両方式ともA4ページ、SinglePage/Fit、抽出したRGB画素一致を満たした。一方、img2pdfの配布依存（pikepdf、lxml、packaging等）は既存Pillowを除いて約20.9MiBだった。4ページでの約0.32秒の短縮とPDFの約4.8%縮小に対し、アプリ配布物が大きく増えるため、ReportLab+pypdfを維持する。

## 画面と入力

- BMP と PNG をファイル選択およびドラッグ＆ドロップで追加する。拡張子の大文字小文字は区別しない。
- 重複する入力パスは一件にまとめる。
- 初期順はファイル名の自然順（大文字小文字を区別せず、数字部分は数値として比較）とする。同名ファイルはフルパス順で安定させる。
- 追加後も利用者がドラッグまたは上下ボタンで順番を変更できる。現在の一覧順をPNG処理とPDFページ順に適用する。
- PNG圧縮レベル0〜9を選び、初期値9とする。BMP/PNGは可逆再圧縮し、画素データと入力側のDPI情報があれば維持する。
- PNGの出力先フォルダーを選択できる。未指定なら各入力画像と同じフォルダーにPNGを出す。フォルダー指定時は全PNGをそのフォルダーに出す。
- PNG入力用のファイル名接尾辞欄を追加し、初期値は `_compressed` とする。接尾辞はPNG入力を再圧縮して出力する場合にだけ付け、BMP入力から生成するPNG名は従来どおり元のベース名を維持する。
- 「上書きする」チェックボックスを追加し、初期状態はオフとする。オンなら出力先に同名の既存ファイルがある場合に置き換える。オフなら既存出力を残し、出力名に連番を付けて新しいファイルを作る。
- 「上書きする」がオンの間はPNG入力用接尾辞欄を編集不可にする。設定済みの接尾辞値と既存の出力名規則は維持する。
- PDFチェックボックスとPDF名入力欄を維持する。PDFはチェック時のみ、全PNG変換成功後に一覧順で一つ作る。保存先ダイアログは維持し、PNG出力フォルダーが指定されている場合はその場所を初期フォルダーとして提示する。
- PDFは画像1枚につき1ページのA4、縦横比維持、余白ありとする。元画像を再サンプリングせず、PNGのDPIをページ上の物理寸法に反映する。PDFを開いた初期状態はページ全体表示・単ページ表示とする。

## 出力と衝突

- BMP入力は従来どおり同じベース名の `.png` を出力する。
- PNG入力は接尾辞欄の文字列を付けた名前で出力する。接尾辞はファイル名に使えない文字やパス区切りを受け付けず、空欄は認めない。
- 上書きチェックがオフの場合、出力名が既存ファイルと衝突するときは連番を付けて一意にする。オンの場合は前回実行などで既にある出力先を置き換える。同じ実行内で複数入力が同名出力になる場合は、チェック状態に関係なく連番で一意にする。
- 入力として選択したBMP/PNGファイル自体は常に保護し、チェックがオンでも上書きしない。入力ファイルと衝突する場合は連番を付ける。
- PDFの保存先に同名ファイルがある場合も同じチェック設定に従う。各出力は一時ファイルへ完成させてから確定し、不完全なファイルを残さない。
- 一部のPNG変換が失敗した場合、成功したPNGは残し、失敗内容を報告し、PDFは作らない。
- PDF作成失敗時は完成済みPNGを残し、PDFのエラーを表示する。

## コード構成

GUIイベント処理と変換ワークフローを分離する。画面は入力選択、一覧、並べ替え、設定、進行状況・結果の表示を担う。ワークフロー層は順序・出力先・エラー方針を扱い、画像変換とPDF出力はGUIに依存しない関数に保つ。責務を超えて小さなファイルを増やさず、現在の規模に見合う3〜4モジュール程度の構成にする。

画像変換とPDF生成は単一のバックグラウンドスレッドで順番に処理し、Tkinterのイベントループはメインスレッドだけで更新する。並列化はせず、画像群の同時展開によるメモリ増加を避ける。

## 依存と配布

- 維持: Tkinter、tkinterdnd2、Pillow、ReportLab、pypdf。
- `img2pdf` は比較で高速・小容量だったが、追加依存が約20.9MiBで配布物を大きくするため採用しない。
- 配布方式は2026-10-10の追記に従い、PyInstaller one-folderへ戻す。利用者が選んだ既存のフォルダー型と同じく、EXEと `_internal` をまとめて配布する。
- リファクタリング前後で同一入力を使い、配布物サイズ、変換・PDF作成時間、ピークメモリを記録する。ユーザー要件の品質・操作に回帰がないことを確認する。

## 配布方式の判断履歴（2026-10-10）

- 利用者PCに管理者権限がないため、インストーラーを使わない。
- 当初はPyInstaller one-folderを採用し、その後にNuitka one-fileへ切り替えた。利用者は既存のフォルダー型を選び、2026-10-10に配布標準をPyInstaller one-folderへ戻すことを決めた。
- `bmp2png_pdf.exe` と `_internal` フォルダーを同じ場所に保って使う。UPX圧縮は無効にする。これは配布形式の指定であり、セキュリティソフトの判定結果を保証するものではない。
- C/C#へのアプリ全面移植はしない。既存Python/Tkinter/Pillowの実装を維持する。

## 初回対象外

C/C#への全面移植、Windows以外の対応、複数PDF出力、画像編集、非可逆圧縮、インストーラー、自動更新、署名、設定の永続化。
